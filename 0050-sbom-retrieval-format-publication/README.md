## Summary

Zarf will allow a package author to declaratively ingest an SBOM (Software Bill of Materials) for an image or file artifact. Package creation will preserve the producer's SBOM when specified otherwise retains the current Syft-generated process. Every declared source is then fail-closed for retrieval, required integrity checks, and format decoding. 

## Motivation

The internals of the package today all dictate declarative packaging, except the outputs of package signing which require distinct and controlled inputs, and SBOMs which are generated by default (or not included at all). This prevents optionality for allowing upstream systems of provenance - particularly the source of truth build or origination systems - to provide SBOMs which could have greater fidelity of information. Separately there is no mechanism to enrich an sbom prior to packaging to include information such as a canonical product identity for the software itself which would enable more accurate scanning results. 

### Goals

- Declarative ingestion of one author-selected SBOM for an image manifest or file.
- Retain Syft image generation when no image SBOM is declared.
- Record the package author's image-manifest or file association for a supplied SBOM.
- Support native Syft JSON, SPDX JSON, and CycloneDX JSON inputs supported by the bundled Syft version.
- Preserve the accepted SBOM bytes in their declared format as the canonical package inventory.
- Retain exactly one canonical SBOM for each declared image manifest or file artifact, and publish the image SBOM when Zarf pushes the corresponding image to a registry.

### Non-Goals

- Select among multiple matching supplier SBOMs. An OCI-referrer source without a descriptor digest succeeds only when its resolved image has exactly one matching referrer.
- Infer a product CPE from an image name, tag, OCI label, package name, or dependency graph.
- Merge two independently produced SBOM inventories.
- Augment an SBOM with any additional information that requires SBOM specific logic in Zarf.

## Proposal

Zarf will introduce `sbom` declarations on images and files. Each declaration contains a required input `format` and one typed `source` for the artifact's effective inventory. When an image declaration is absent, Zarf generates the inventory with Syft. A file without a declaration retains existing packaging behavior. When a declaration is present, its source must retrieve, pass required integrity checks, and decode as its declared format or package creation fails.

```yaml
components:
  - name: applicationstart
    images:
      - name: registry.example/app:1.2.3
        sbom:
          format: cyclonedx-json
          source:
            local:
              path: ./sboms/example-application.cdx.json
```

Zarf resolves an image reference to an immutable digest before retrieving the declared SBOM. A package-local `sbom` is accepted only when the reference resolves to one image manifest. If an image reference resolves to an image index, package creation rejects an `sbom` declaration. Without a declaration, the existing Syft fallback continues to generate inventory for each platform manifest.

Before retrieval, Zarf groups every image occurrence by its resolved leaf manifest digest. A group with no declaration generates one Syft SBOM. A group with one normalized declaration, including repeated identical declarations, retrieves that source once and creates one source-backed record. A group with different normalized declarations fails package creation rather than choosing a supplier by component order. Normalization includes the format and complete source configuration after path, URL, and digest normalization. The resulting record is the package author's association of one effective canonical SBOM with that manifest; payload association validation is deferred.

For a file, the `sbom` declaration applies only to a regular source file. Its associated artifact identity is the content digest of the source file resolved during package creation, before destination placement, archive extraction, or deploy-time templating. Files that represent directories, extracted archives, templated output, or multiple files cannot declare an SBOM. Payload association validation against that identity is deferred.

### User Stories

#### Story 1: Consume a release SBOM

As a package author, I want to bind my producer-generated SBOM to the image I package so the package retains the inventory generated by my release process.

#### Story 2: Build in a disconnected environment

As a package author building offline, I want to provide a local SBOM file so Zarf does not need network access to reconstruct inventory that my build already produced.


### Risks and Mitigations

**Risk:** A supplied SBOM may describe a different image manifest, platform, or file.

**Mitigation:** In Phases 1–3, retain supplier evidence and record the package author's declared association. Phase 4 will require direct SBOM subject evidence or a verified external binding before treating that association as validated. OCI referrer resolution continues to validate the OCI artifact manifest's `subject`; that binds the referrer artifact, not necessarily the SBOM payload it carries.

#### Conflicting inventories

**Risk:** Accepting more than one supplier inventory could create facts not asserted by either producer.

**Mitigation:** Accept one explicit supplier SBOM or generate one with Syft. An OCI-referrer source without a descriptor digest accepts only one matching candidate; zero or multiple matches fail package creation. Do not select among or merge supplier inventories.


#### Input and output fidelity

**Risk:** Explicit conversion for a user-requested export can discard producer-specific information.

**Mitigation:** Preserve the accepted document bytes, declared format, and content digest as the canonical package SBOM. Conversion is an explicit export operation and does not replace the preserved document.

#### Registry publication failure

**Risk:** A target registry may lack the OCI Distribution Spec 1.1 Referrers API or concurrent publishers may overwrite a fallback referrers index.

**Mitigation:** Publish artifacts with an immutable `subject` digest. Use the Referrers API when available; otherwise maintain the standard digest-derived referrers-tag image index. Use conditional updates where supported and fail if Zarf cannot confirm that the SBOM descriptor remains associated with its image.

## Design Details

### Graduation Criteria

#### Phase 1: Declarative in-package ingestion and formatting

Introduce one optional `sbom` declaration for an image manifest or regular file, with a package-local source. Reject an image declaration for an image index, because this feature does not define platform-to-source mapping. For files, accept only a regular source file and record its resolved content digest before archive extraction, destination placement, or deploy-time templating. Retrieve the source, preserve its accepted bytes and declared format as the canonical package SBOM in Zarf's content-addressed `sboms/` store, and decode it to validate the declared format. Preserve the existing Syft-generation fallback, including per-platform generation for an image index without an `sbom` declaration. This phase establishes the one-SBOM-to-one-artifact package contract with author-declared artifact association.

#### Phase 2: Registry publication during deployment

When deployment pushes an image manifest, construct a subject-bound OCI artifact wrapper around the already packaged canonical SBOM payload and publish it to the target registry. Use the Referrers API when available and the OCI referrers-tag fallback otherwise. This phase does not discover supplier SBOMs. This will set the pattern for re-use with artifacts such as signatures.

#### Phase 3: Remote and OCI-referrer source retrieval

Add content-pinned `remote` and `ociReferrer` source kinds. A remote source remains author-selected. An image `ociReferrer` source uses the resolved image repository: it fetches an explicitly pinned referrer descriptor when `digest` is present, or discovers exactly one matching referrer when `digest` is absent. Discovery queries the Referrers API first; only when that API is unsupported does Zarf read the standard digest-derived referrers-tag index. Authentication, transport, server, or malformed-response failures do not trigger the fallback. OCI referrer resolution validates the artifact manifest's `subject`; both modes fail package creation when retrieval, integrity checks, source resolution, or format decoding cannot establish one accepted supplier SBOM. File declarations support `remote` but not `ociReferrer`.

#### Phase 4: Artifact association validation

Define the format-specific direct subject rules and verified external binding evidence that prove a supplier SBOM describes its declared image manifest or regular file. Require that proof before treating the association as validated. This phase does not change source retrieval or the preserved supplier representation.


### SBOM selection

#### Image SBOM sources

An image `sbom` declaration requires `format` and `source`. `format` is one of `syft-json`, `spdx-json`, or `cyclonedx-json`; it selects the input decoder and syntactic validation. `source` is an exact one-of union:

- `local.path` identifies a local file. Phase 1 supports this kind only; its path uses Zarf's existing local-file retrieval behavior, including paths outside the package directory.
- `remote.url` identifies an `http` or `https` file and requires `remote.checksum` using Zarf's existing `<algorithm>:<digest>` checksum grammar.
- `ociReferrer.digest` optionally pins one OCI referrer artifact manifest in the resolved image's repository. When `digest` is present, Zarf fetches that descriptor and validates that it is a matching referrer. When absent, Zarf queries referrers for the resolved image digest and accepts exactly one descriptor matching the declared format. If the Referrers API is unsupported, Zarf derives the standard referrers tag, validates its OCI index, and applies the same match rule. Zero or multiple matches fail.

During component import, the base component's image `sbom` declaration wins with the existing image merge behavior. An image manifest with no declaration uses Syft generation; a manifest with a declaration either retrieves and decodes its source or fails package creation.

#### File SBOM sources

A file `sbom` declaration accepts the same `format`, `local.path`, and `remote.url` / `remote.checksum` semantics as an image declaration. Its source union deliberately omits `ociReferrer`; schema validation rejects that field for files. A file with a declaration either retrieves and decodes its source or fails package creation.


### Publication and provenance

Zarf's canonical package-internal SBOM is the accepted supplier document in its declared format. Zarf stores each accepted document once in a content-addressed `sboms/` directory keyed by its content digest. An artifact record maps each image manifest or regular-file identity to that stored document. Zarf will:

1. retain the accepted document bytes as the canonical package inventory;
2. record its declared format, source location, and content digest as supplier evidence;
3. decode the document according to its declared format to validate that format; and
4. perform conversion only as an explicit `zarf tools sbom` export operation.

The package does not duplicate the canonical document as an OCI artifact. Package inspection and viewing must read the recorded format. Explicit conversion does not replace or mutate the canonical supplier document.

### Registry publication

The package records one canonical SBOM record per resolved image manifest. Registry publication reads the package's preserved SBOM payload; it must not generate, convert, or duplicate a second package inventory during deployment.

Before Phase 4, this is an author-declared association. The OCI `subject` on a published artifact binds that target-registry artifact to the target image manifest, but does not prove that its supplier SBOM payload describes the image.

For every unique target repository and target image manifest digest, Zarf:

1. resolves the package's canonical SBOM payload, format, and content digest from `sboms/`;
2. derives a target-specific OCI artifact manifest and expected descriptor using the recorded format's OCI payload media type and the target image manifest digest;
3. coordinates concurrent component work by that repository-and-digest key;
4. succeeds without mutation when the exact expected descriptor is already attached; or
5. publishes the immutable preserved payload and target-specific artifact manifest, then attaches its descriptor using the Referrers API when available or the referrers-tag fallback otherwise.

The fallback tag is the digest-derived referrers tag defined by the OCI Distribution Spec, for example `sha256-<encoded-digest>`. Zarf validates the existing OCI index, preserves every existing descriptor, and treats descriptor identity as its media type, digest, and size. It avoids duplicate descriptors and uses conditional updates when the registry supports them.

The recorded input format selects the registry artifact payload media type. CycloneDX, SPDX, and Syft inputs are published in that same respective format; deployment never applies a converter-version-dependent projection.

### Test Plan

- Phase 1 unit and integration tests cover `local` declarations for a single image manifest and a regular file; paths outside the package directory; image-index rejection; repeated identical declarations resolving to one SBOM record and one content-addressed stored document; rejection for differing declarations resolving to one manifest; rejection for directories, extracted archives, templated output, and multi-file artifacts; existing per-platform Syft fallback for an index without a declaration; the three supported format values; retrieval and decoding failures; preservation of exact supplier bytes, format, and content digest; recorded author-declared association; one-to-one artifact association; and Syft fallback.
- Phase 2 deployment tests cover a registry with the Referrers API and a registry that requires the referrers-tag fallback. They assert one publication for repeated component references to the same target repository and manifest; separate publication for the same manifest copied to different repositories; a target-specific wrapper around the preserved payload; exact-descriptor idempotence; publication of preserved supplier bytes with the recorded format's media type; digest subject binding; preservation of unrelated fallback-index descriptors; and a failed deployment result when publication is unconfirmed.
- Phase 3 tests cover `http` and `https` retrieval with content-digest validation; pinned OCI referrer retrieval; unpinned OCI referrer retrieval with exactly one match through both the Referrers API and referrers-tag fallback; OCI artifact-subject mismatch; and failure for zero or multiple matching referrers, malformed Referrers API responses, unsupported APIs with no valid fallback index, and content digests.
- Phase 4 tests cover format-specific direct subject evidence and verified external binding evidence for matching and mismatched image-manifest and regular-file identities.

### Upgrade / Downgrade Strategy

Images with no `sbom` declaration retain current Syft SBOM generation behavior; files with no declaration retain existing packaging behavior. A package that uses this field requires a Zarf version that supports the introduced API schema and must fail clearly on an older CLI rather than silently dropping the declaration.

Removing a declaration restores generated inventory for the image. Removing a supplier SBOM from a package does not alter the preserved bytes in packages that were already built.

### Version Skew Strategy

This feature changes the v1beta1 package schema.

## Drawbacks

This adds schema, source-validation, format-aware package inspection, and provenance complexity to package creation. Restricting the feature to one explicit supplier source avoids unsafe merging but does not cover workflows that require multiple independently produced inventories.

## Alternatives

### Continue generating SBOMs exclusively with Syft

Syft remains the fallback, but exclusive generation discards an application producer's authoritative inventory and cannot reliably infer every primary application identity.

### Add CPEs to discovered packages

Appending a declared CPE to a dependency or Go-module component conflates product identity with dependency identity and is not a reliable scanner interoperability model.

### Merge multiple SBOMs

Zarf accepts only one supplier SBOM for a manifest. No general component identity or relationship merge is safe across independent SBOM producers; a merge can create false inventory or scanner findings.


### Publish SBOMs as unrelated files or tags

Publishing a sidecar file or a tag-derived SBOM without a manifest subject loses the required artifact binding. OCI referrers, with the standard referrers-tag fallback, retain that binding on compatible and older registries.

## Infrastructure Needed

No new permanent infrastructure is required. OCI-referrer coverage needs test registries with and without the OCI Distribution Spec 1.1 Referrers API.
