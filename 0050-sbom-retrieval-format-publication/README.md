## Summary

Software Bill of Materials (SBOM) should be an optional artifact for packaging alongside the container images they were built from. This enables users to control the fidelity of information they are packaging when they rely on the SBOM for downstream delivery or consumption.

## Motivation

The internals of the package today all dictate declarative packaging, except the outputs of package signing which require distinct and controlled inputs, and SBOMs which are generated by default or not included at all. This prevents optionality for allowing upstream systems of provenance - particularly the source of truth build or origination systems - to provide SBOMs which could have greater fidelity of information.

An image tag or index can refer to several platform builds whose contents and inventories differ. A single image-level SBOM is therefore ambiguous. The proposal makes the platform-specific image the unit of association and carries that association through packaging and registry publication.

### Goals

- Represent each packaged platform image with its platform and immutable manifest digest.
- Allow each platform-specific image to declare one author-selected SBOM.
- Retain Syft image generation when a platform-specific image has no supplier SBOM.
- Bind each supplied SBOM to exactly one packaged image manifest and preserve that association through packaging and publication.
- Support native Syft JSON, SPDX JSON, and CycloneDX JSON inputs supported by the bundled Syft version.
- Preserve the accepted SBOM bytes in their declared format as the canonical package inventory.
- Retain exactly one canonical SBOM for each packaged image manifest and publish it when Zarf pushes that image to a registry.

### Non-Goals

- Select among multiple matching supplier SBOMs. An OCI-referrer source without a descriptor digest succeeds only when the selected leaf manifest has exactly one matching referrer.
- Treat an image-index SBOM as a per-platform SBOM. Index-level aggregate SBOMs are outside this proposal.
- Merge two independently produced SBOM inventories.
- Augment an SBOM with any additional information that requires SBOM-specific logic in Zarf.
- Add declarative SBOM ingestion or generation for files. Existing file packaging behavior is unchanged.

## Proposal

Zarf will introduce an optional `sbom` declaration on each platform-specific image manifest entry. An image entry maps its logical image reference to one or more platform-specific images. Each entry contains a `platform`, the immutable image manifest `digest`, and, optionally, an `sbom` containing a required input `format` and one typed `source`. When an entry has no supplier SBOM, Zarf generates its inventory with Syft. When a declaration is present, its source must retrieve, pass required integrity checks, and decode as its declared format or package creation fails.

### Terminology

- **Image reference:** The name a package author writes, such as `registry.example/app:1.2.3`.
- **Platform-specific image:** One build of that image for an operating system and architecture, such as `linux/amd64`.
- **Image manifest:** The OCI object describing one platform-specific image. Its digest is the immutable identifier for that exact image.
- **Image index:** An OCI object that points to multiple platform-specific image manifests.

The proposal uses “leaf manifest” in the technical sections as shorthand for a platform-specific image manifest, to distinguish it from an image index.

```yaml
components:
  - name: application
    images:
      - name: registry.example/app:1.2.3
        manifests:
          - platform: linux/amd64
            digest: sha256:image-amd64
            sbom:
              format: cyclonedx-json
              source:
                ociReferrer: {}

          - platform: linux/arm64
            digest: sha256:image-arm64
            sbom:
              format: cyclonedx-json
              source:
                local:
                  path: ./sboms/app-arm64.json
```

Each `manifests[]` entry identifies one platform-specific leaf image manifest. A digest-pinned leaf-manifest image reference is inherently single-platform and produces one manifest entry. An image index or tag resolving to an index requires one manifest entry per packaged platform when supplier SBOMs are declared; Zarf must not apply one supplier SBOM to every platform. Without a supplier declaration on a manifest entry, the existing Syft fallback generates inventory for that leaf manifest.

Before retrieval, Zarf groups every image occurrence by its manifest platform and digest. A group with no supplier declaration generates one Syft SBOM. A group with one normalized declaration, including repeated identical declarations, retrieves that source once and creates one source-backed record. A group with different normalized declarations fails package creation rather than choosing a supplier by component order. Normalization includes the manifest platform, image digest, SBOM format, and complete source configuration after path, URL, and digest normalization. The resulting record is the package author's association of one effective canonical SBOM with one leaf manifest; payload association validation is deferred.

### Platform-aware image resolution

This ZEP depends on a shared image-resolution contract in which an image's `manifests[]` entries map platforms to exactly one leaf image manifest digest.

For an image index, the resolver selects the descriptor matching each requested package platform and fails when no descriptor or more than one descriptor matches. For a leaf-manifest reference, the resolved digest is the image identity and the image is inherently single-platform. Every `manifests[].digest` value must identify the leaf manifest for its declared platform before Zarf retrieves or publishes its SBOM.

Every image SBOM record stores the manifest platform as metadata and the manifest digest as its binding identity. A supplier document may be reused as stored content for multiple manifest entries only when the author declares each association explicitly.

### User Stories

#### Story 1: Consume a release SBOM

As a package author, I want to bind my producer-generated SBOM to the image I package so the package retains the inventory generated by my release process.

#### Story 2: Build in a disconnected environment

As a package author building offline, I want to provide a local SBOM file so Zarf does not need network access to reconstruct inventory that my build already produced.

#### Story 3: Package a platform-specific image and SBOM

As a package author, I want package creation to select the image manifest for its target platform and bind the matching supplier SBOM to that leaf manifest, without reusing an SBOM from another platform.


**Risk:** A supplied SBOM may describe a different image manifest or platform.

**Mitigation:** Resolve the image platform before retrieving its SBOM and retain the selected leaf manifest digest as supplier evidence. In Phases 1–3, record the package author's declared association. Phase 4 will require direct SBOM subject evidence or a verified external binding before treating that association as validated. OCI referrer resolution validates that the referrer artifact manifest's `subject` equals the selected leaf manifest; that binds the referrer artifact, not necessarily the SBOM payload it carries.

#### Conflicting inventories

**Risk:** Accepting more than one supplier inventory could create facts not asserted by either producer.

**Mitigation:** Accept one explicit supplier SBOM or generate one with Syft for each selected leaf manifest. An OCI-referrer source without a descriptor digest accepts only one matching candidate for that leaf manifest; zero or multiple matches fail package creation. Do not select among or merge supplier inventories.


#### Input and output fidelity

**Risk:** Explicit conversion for a user-requested export can discard producer-specific information.

**Mitigation:** Preserve the accepted document bytes, declared format, and content digest as the canonical package SBOM. Conversion is an explicit export operation and does not replace the preserved document.

#### Registry publication failure

**Risk:** A target registry may lack the OCI Distribution Spec 1.1 Referrers API or concurrent publishers may overwrite a fallback referrers index.

**Mitigation:** Publish artifacts with an immutable `subject` digest. Use the Referrers API when available; otherwise maintain the standard digest-derived referrers-tag image index. Use conditional updates where supported and fail if Zarf cannot confirm that the SBOM descriptor remains associated with its image.

## Design Details

### Graduation Criteria

#### Phase 1: Declarative in-package ingestion and formatting

Introduce the shared platform-aware image resolution contract and one optional `sbom` declaration on each `manifests[]` entry, with a local source. Each manifest entry supplies the platform-specific leaf manifest digest; the image schema owns how those entries are resolved or author-provided. Retrieve each declared source, preserve its accepted bytes and declared format as the canonical package SBOM in Zarf's content-addressed `sboms/` store, and decode it to validate the declared format. Preserve the existing Syft-generation fallback for manifest entries without a supplier declaration. This phase establishes the one-SBOM-to-one-leaf-manifest package contract with explicit platform and digest metadata. File SBOM ingestion and generation remain unchanged and are outside this ZEP.

#### Phase 2: Registry publication during deployment

When deployment pushes an image platform manifest, construct a subject-bound OCI artifact wrapper around the already packaged canonical SBOM payload and publish it to the target registry. Use the Referrers API when available and the OCI referrers-tag fallback otherwise. Publish against the actual target leaf manifest digest selected by the platform-aware image resolution process. This phase does not discover supplier SBOMs.

#### Phase 3: Remote and OCI-referrer source retrieval

Add content-pinned `remote` and `ociReferrer` source kinds. A remote source remains author-selected. An image `ociReferrer` source uses the selected image repository and leaf manifest digest: it fetches an explicitly pinned referrer descriptor when `digest` is present, or discovers exactly one matching referrer when `digest` is absent. Discovery queries the Referrers API for the leaf digest first; only when that API is unsupported does Zarf read the standard digest-derived referrers-tag index for that same leaf digest. Authentication, transport, server, or malformed-response failures do not trigger the fallback. OCI referrer resolution validates that the artifact manifest's `subject` equals the selected leaf manifest digest. A referrer attached only to an image index does not satisfy a platform SBOM declaration. Both modes fail package creation when retrieval, integrity checks, source resolution, or format decoding cannot establish one accepted supplier SBOM.

#### Phase 4: Artifact association validation

Define the format-specific direct subject rules and verified external binding evidence that prove a supplier SBOM describes its selected image leaf manifest. Require that proof before treating the association as validated. This phase does not change platform resolution, source retrieval, or the preserved supplier representation.


### SBOM selection

#### Image SBOM sources

Each `images[].manifests[]` entry contains a `platform`, an immutable image manifest `digest`, and an optional `sbom`. An `sbom` requires `format` and `source`; `format` is one of `syft-json`, `spdx-json`, or `cyclonedx-json` and selects the input decoder and syntactic validation. A digest-pinned leaf-manifest image reference is inherently single-platform and produces one manifest entry. An image index or tag resolving to an index requires one manifest entry per packaged platform when supplier SBOMs are declared.

`source` is an exact one-of union:

- `local.path` identifies a local SBOM document. Phase 1 supports this kind only; its path uses Zarf's existing local-file retrieval behavior, including paths outside the package directory.
- `remote.url` identifies an `http` or `https` SBOM document and requires `remote.checksum` using Zarf's existing `<algorithm>:<digest>` checksum grammar.
- `ociReferrer.digest` optionally pins one OCI referrer artifact manifest in the resolved image repository. When `digest` is present, Zarf fetches that descriptor and requires its artifact manifest `subject` to equal the selected leaf manifest digest. When absent, Zarf queries referrers for that leaf digest and accepts exactly one descriptor matching the declared format. If the Referrers API is unsupported, Zarf derives the standard referrers tag from that leaf digest, validates its OCI index, and applies the same match rule. Zero or multiple matches fail.

The manifest platform and digest are part of the normalized association. During component import, manifest entries are merged by platform using the existing image merge behavior; conflicting entries for the same platform fail rather than being selected by component order. A manifest entry without `sbom` uses Syft generation; an entry with `sbom` either retrieves and decodes its source or fails package creation. One supplier declaration must not implicitly apply to another manifest entry.

### Publication and provenance

Zarf's canonical package-internal SBOM is the accepted supplier document in its declared format. Zarf stores each accepted document once in a content-addressed `sboms/` directory keyed by its content digest. An artifact record maps each selected image platform and leaf manifest digest to that stored document. Zarf will:

1. retain the accepted document bytes as the canonical package inventory;
2. record its declared format, source location, selected platform, leaf manifest digest, and content digest as supplier evidence;
3. decode the document according to its declared format to validate that format; and
4. perform conversion only as an explicit `zarf tools sbom` export operation.

The package does not duplicate the canonical document as an OCI artifact. Package inspection and viewing must read the recorded format. Explicit conversion does not replace or mutate the canonical supplier document.

### Registry publication

The package records one canonical SBOM association per selected image leaf manifest. Registry publication reads the package's preserved SBOM payload; it must not generate, convert, or duplicate a second package inventory during deployment.

Before Phase 4, this is an author-declared association. The OCI `subject` on a published artifact binds that target-registry artifact to the target leaf manifest, but does not prove that its supplier SBOM payload describes the image.

For every unique target repository and target leaf manifest digest, Zarf:

1. resolves the package's canonical SBOM payload, format, and content digest from `sboms/`;
2. derives a target-specific OCI artifact manifest and expected descriptor using the recorded format's OCI payload media type and the target leaf manifest digest;
3. coordinates concurrent component work by that repository-and-leaf-digest key;
4. succeeds without mutation when the exact expected descriptor is already attached; or
5. publishes the immutable preserved payload and target-specific artifact manifest, then attaches its descriptor using the Referrers API when available or the referrers-tag fallback otherwise.

The fallback tag is the digest-derived referrers tag defined by the OCI Distribution Spec, for example `sha256-<encoded-leaf-digest>`. Zarf validates the existing OCI index, preserves every existing descriptor, and treats descriptor identity as its media type, digest, and size. It avoids duplicate descriptors and uses conditional updates when the registry supports them.

The recorded input format selects the registry artifact payload media type. CycloneDX, SPDX, and Syft inputs are published in that same respective format; deployment never applies a converter-version-dependent projection.

### Test Plan

- Phase 1 unit and integration tests cover `manifests[]` resolution of image indexes to leaf manifests; author-provided platform-digest mappings; leaf-digest image references; missing and ambiguous platform matches; local SBOM declarations on one image manifest; paths outside the package directory; repeated identical declarations resolving to one SBOM record and one content-addressed stored document; rejection for conflicting declarations or digests for one platform; rejection of implicit cross-platform reuse; existing per-platform Syft fallback for manifest entries without supplier declarations; the three supported format values; retrieval and decoding failures; preservation of exact supplier bytes, format, and content digest; recorded platform and leaf-digest association; and one-to-one artifact association.
- Phase 2 deployment tests cover a registry with the Referrers API and a registry that requires the referrers-tag fallback. They assert one publication for repeated references to the same target repository and leaf manifest; separate publication for distinct target platforms and repositories; a target-specific wrapper around the preserved payload; exact-descriptor idempotence; publication of preserved supplier bytes with the recorded format's media type; leaf-digest subject binding; preservation of unrelated fallback-index descriptors; and a failed deployment result when publication is unconfirmed.
- Phase 3 tests cover `http` and `https` retrieval with content-digest validation; pinned OCI referrer retrieval whose subject matches the selected leaf digest; unpinned OCI referrer retrieval with exactly one match through both the Referrers API and referrers-tag fallback; rejection of index-subject referrers for platform declarations; and failure for zero or multiple matching referrers, malformed Referrers API responses, unsupported APIs with no valid fallback index, and invalid content digests.
- Phase 4 tests cover format-specific direct subject evidence and verified external binding evidence for matching and mismatched leaf-manifest identities.

### Upgrade / Downgrade Strategy

Image manifest entries with no supplier `sbom` retain current Syft SBOM generation behavior. File SBOM ingestion and generation remain unchanged and outside this ZEP. A package that uses platform-aware image mappings or this SBOM field requires a Zarf version that supports the introduced API schema and must fail clearly on an older CLI rather than silently dropping the declaration.

Removing a supplier `sbom` from a manifest entry restores generated inventory for that image platform. Removing a supplier SBOM from a package definition does not alter the preserved bytes in packages that were already built.

### Version Skew Strategy

This feature changes the v1beta1 package schema and depends on the platform-aware image resolution contract. The schema migration must preserve explicit `manifests[]` platform-to-leaf-digest mappings and reject conversions that cannot represent an image's platform associations without loss.

## Drawbacks

This adds schema, source-validation, format-aware package inspection, and provenance complexity to package creation. Restricting the feature to one explicit supplier source avoids unsafe merging but does not cover workflows that require multiple independently produced inventories.

## Alternatives

### Continue generating SBOMs exclusively with Syft

Syft remains the fallback, but exclusive generation discards an application producer's authoritative inventory and cannot reliably infer every primary application identity.

### Add CPEs to discovered packages

Appending a declared CPE to a dependency or Go-module component conflates product identity with dependency identity and is not a reliable scanner interoperability model.

### Merge multiple SBOMs

Zarf accepts only one supplier SBOM for a manifest. No general component identity or relationship merge is safe across independent SBOM producers; a merge can create false inventory or scanner findings.


### Publish SBOMs as unrelated files or tags

Publishing a sidecar file or a tag-derived SBOM without a manifest subject loses the required artifact binding. OCI referrers, with the standard referrers-tag fallback, retain that binding on compatible and older registries.

## Infrastructure Needed

No new permanent infrastructure is required. OCI-referrer coverage needs test registries with and without the OCI Distribution Spec 1.1 Referrers API.
