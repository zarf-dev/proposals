## Summary

Software Bill of Materials (SBOM) should be an optional artifact for packaging alongside the container images they were built from. This enables users to control the fidelity of information they are packaging when they rely on the SBOM for downstream delivery or consumption.

## Motivation

The internals of the package today all dictate declarative packaging, except the outputs of package signing which require distinct and controlled inputs, and SBOMs which are generated by default or not included at all. This prevents optionality for allowing upstream systems of provenance - particularly the source of truth build or origination systems - to provide SBOMs which could have greater fidelity of information.

An image tag or index can refer to several platform builds whose contents and inventories differ. A single image-level SBOM is therefore ambiguous. The proposal makes the platform-specific image the unit of association and carries that association through packaging and registry publication.

### Goals

- Represent each packaged platform image with its platform and immutable manifest digest.
- Allow each platform-specific image to declare one author-selected SBOM.
- Retain Syft image generation when a platform-specific image has no supplier SBOM.
- Bind each supplied SBOM to exactly one packaged image manifest and preserve that association through packaging and publication.
- Support native Syft JSON, SPDX JSON, and CycloneDX JSON inputs supported by the bundled Syft version.
- Preserve the accepted SBOM bytes in their declared format as the canonical package inventory.
- Retain exactly one canonical SBOM for each packaged image manifest and publish it when Zarf pushes that image to a registry.

### Non-Goals

- Select among multiple matching supplier SBOMs. An OCI-referrer source without a descriptor digest succeeds only when the selected leaf manifest has exactly one matching referrer.
- Treat an image-index SBOM as a per-platform SBOM. Index-level aggregate SBOMs are outside this proposal.
- Merge two independently produced SBOM inventories.
- Augment an SBOM with any additional information that requires SBOM-specific logic in Zarf.
- Add declarative SBOM ingestion or generation for files. Existing file packaging behavior is unchanged.

## Proposal

Zarf will associate an optional supplier SBOM with each platform-specific image manifest entry. Each entry identifies a platform and immutable image manifest digest, and may contain an SBOM format and source. Zarf preserves the supplied document and publishes it with the corresponding image. When an entry has no supplier SBOM, Zarf generates one with Syft. A declared source that cannot be retrieved, verified, or decoded causes package creation to fail.

### Terminology

- **Image reference:** The name a package author writes, such as `registry.example/app:1.2.3`.
- **Platform-specific image:** One build of that image for an operating system and architecture, such as `linux/amd64`.
- **Image manifest:** The OCI object describing one platform-specific image. Its digest is the immutable identifier for that exact image.
- **Image index:** An OCI object that points to multiple platform-specific image manifests.

The proposal uses “leaf manifest” in the technical sections as shorthand for a platform-specific image manifest, to distinguish it from an image index.

```yaml
components:
  - name: application
    images:
      - name: registry.example/app:1.2.3
        manifests:
          - platform: linux/amd64
            digest: sha256:image-amd64
            sbom:
              format: cyclonedx-json
              source:
                ociReferrer: {}

          - platform: linux/arm64
            digest: sha256:image-arm64
            sbom:
              format: cyclonedx-json
              source:
                local:
                  path: ./sboms/app-arm64.json
```

Each `manifests[]` entry identifies one platform-specific image. An image index or tag resolving to an index requires one entry per packaged platform when supplier SBOMs are declared. Zarf must not apply one platform's supplier SBOM to another platform. A manifest entry without an SBOM uses the Syft fallback.

The shared image-resolution contract maps each platform to exactly one image manifest digest. Zarf verifies that every `manifests[].digest` identifies the image for its declared platform before retrieving or publishing its SBOM. A supplier document may be reused as stored content for multiple platforms only when each association is declared explicitly.

### User Stories

#### Story 1: Consume a supplier SBOM

As a package author, I want to include the SBOM produced by an upstream image builder to the image I package, so the package retains the inventory generated by that release process.

#### Story 2: Prepare and enrich an SBOM

As a package author consuming an image produced by another team or vendor, I want to obtain or generate an SBOM for the exact platform-specific image, enrich it with additional product or package metadata, and provide the resulting SBOM to Zarf, so I can preserve the inventory I need without requiring Zarf to perform the enrichment.

#### Story 3: Consume the published SBOM

As a downstream scanner or operator, I want the preserved SBOM to remain attached to the exact image manifest it describes, so I can retrieve the intended inventory from the target registry.

### Risks and Mitigations

#### Wrong image or platform association

**Risk:** A supplied SBOM may describe a different image or platform.

**Mitigation:** Bind every supplier SBOM to one platform-specific image manifest digest. OCI referrers must have a matching `subject`. Later validation will require direct SBOM subject evidence or verified external binding before treating the payload association as proven.

#### SBOM correctness and completeness

**Risk:** A supplier SBOM may be validly encoded and correctly associated with an image while still being incomplete, inaccurate, or intentionally misleading. A valid signature proves that a trusted signer made or approved the claim; it does not prove that the claim is semantically correct.

**Mitigation:** Zarf validates source integrity, format validity, and image association to a defined extent, but cannot generally prove that an SBOM truthfully or completely describes an image. Preserve supplier bytes and source evidence, distinguish a declared association from an independently validated association, and do not present association validation as content-correctness validation. Downstream consumers remain responsible for trust and completeness policy.

#### Input and output fidelity

**Risk:** Converting a supplier SBOM can discard producer-specific information.

**Mitigation:** Preserve the accepted document bytes and declared format as the canonical package inventory. Conversion is an explicit export operation and does not replace the preserved document.

#### Registry publication failure

**Risk:** A target registry may not support the OCI Referrers API, or concurrent publishers may update its fallback index.

**Mitigation:** Publish a subject-bound artifact using the Referrers API when available and the standard referrers-tag fallback otherwise. Preserve existing associations and fail if Zarf cannot confirm that the SBOM remains attached to the target image.

## Design Details

### Graduation Criteria

#### Phase 1: Attach supplier SBOMs during package creation

Package authors can declare a local SBOM for an image manifest entry. Zarf resolves or validates the entry's platform and image manifest digest, retrieves and decodes the SBOM, preserves the original bytes and format, and records the association. Entries without a supplier SBOM retain the existing Syft generation behavior. Image indexes require separate manifest entries for the packaged platforms.

#### Phase 2: Publish supplier SBOMs with images

When Zarf pushes a packaged image manifest to a registry, it publishes the preserved SBOM for that manifest as a subject-bound artifact. Publication must use the OCI Referrers API when available and the standard referrers-tag fallback otherwise. Deployment must not generate a different SBOM or silently publish an SBOM for another platform.

#### Phase 3: Support remote and OCI-referrer sources

Add checksummed HTTP(S) sources and OCI-referrer sources. Pinned referrers must identify the selected image manifest. Unpinned discovery must find exactly one matching referrer for that manifest. Retrieval, integrity, subject-binding, or format-decoding failures stop package creation.

#### Phase 4: Validate SBOM-to-image association

Define the format-specific subject evidence or verified external binding required to prove that a supplier SBOM describes its selected image manifest. Until that evidence is defined and implemented, the association remains an author declaration. This validates the SBOM-to-image association, not the completeness or semantic correctness of the SBOM contents.

### SBOM selection

#### Image SBOM sources

Each `images[].manifests[]` entry contains a `platform`, an immutable image manifest `digest`, and an optional `sbom`. The `sbom` contains a supported `format` and exactly one source:

- `local.path` for a local SBOM document.
- `remote.url` with `remote.checksum` for a checksummed HTTP(S) SBOM document.
- `ociReferrer.digest` for an optionally pinned SBOM referrer in the image repository.

For an OCI referrer, Zarf requires the artifact's `subject` to match the image manifest digest. Without a pinned referrer digest, Zarf accepts exactly one matching referrer and fails on zero or multiple matches. A manifest entry without `sbom` uses Syft. One entry's SBOM must not implicitly apply to another platform.

During component import, manifest entries are merged by platform using the existing image merge behavior. Conflicting entries for the same platform fail rather than being selected by component order.

### Publication and provenance

Zarf's canonical package SBOM is the accepted supplier document in its declared format. The package preserves the document bytes, format, source evidence, platform, and image manifest digest as one association. During package creation, Zarf records the resolved associations in `BuildData.ImageSBOMs`: authored `images[].manifests[]` entries describe intent, while build metadata records what was actually accepted and shipped. Each record includes the image manifest identity, platform, SBOM payload identity, format, and whether the document was supplier-provided or Syft-generated. Explicit export conversion must not replace the preserved supplier document.

### Registry publication

For every packaged image manifest, deployment reads the resolved association from `BuildData.ImageSBOMs` and publishes the associated preserved SBOM to the target image repository. The published artifact is subject-bound to that image manifest, uses the recorded SBOM format, and is idempotent. Existing unrelated referrers must remain intact. Publication failure must fail deployment rather than silently omitting the SBOM.

### Test Plan

- Phase 1 tests cover manifest-level platform and digest mappings; recording resolved associations for aliases, fallback-generated images, and final packaged manifests; local SBOM retrieval; format decoding; exact-byte preservation; supplier-versus-generated status; conflicting mappings; and rejection of cross-platform reuse.
- Phase 2 tests cover subject-bound publication through both the Referrers API and referrers-tag fallback, idempotent repeated publication, preservation of unrelated referrers, and deployment failure when publication cannot be confirmed.
- Phase 3 tests cover checksummed HTTP(S) retrieval, pinned and unpinned OCI-referrer retrieval, subject mismatches, zero or multiple matches, malformed responses, and invalid digests.
- Phase 4 tests cover direct subject evidence and verified external bindings for matching and mismatched image manifests.

### Upgrade / Downgrade Strategy

Image manifest entries without supplier `sbom` retain current Syft generation behavior. File SBOM ingestion and generation remain unchanged and outside this ZEP. A package using platform-aware image mappings or supplier SBOMs requires a Zarf version that supports the schema and must fail clearly on an older CLI rather than silently dropping the declaration.

Removing an entry's supplier `sbom` restores generated inventory for that image platform. Removing a supplier SBOM from a package definition does not alter preserved bytes in packages that were already built.

### Version Skew Strategy

This feature changes the v1beta1 package schema and depends on the platform-aware image resolution contract. Schema migration must preserve `manifests[]` platform-to-image-digest mappings and reject conversions that cannot represent those associations without loss.

## Drawbacks

This adds schema, source-validation, format-aware package inspection, and provenance complexity to package creation. Restricting the feature to one explicit supplier source avoids unsafe merging but does not cover workflows that require multiple independently produced inventories.

## Alternatives

### Continue generating SBOMs exclusively with Syft

Syft remains the fallback, but exclusive generation discards an application producer's authoritative inventory and cannot reliably infer every primary application identity.

### Add CPEs to discovered packages

Appending a declared CPE to a dependency or Go-module component conflates product identity with dependency identity and is not a reliable scanner interoperability model.

### Merge multiple SBOMs

Zarf accepts only one supplier SBOM for a manifest. No general component identity or relationship merge is safe across independent SBOM producers; a merge can create false inventory or scanner findings.


### Publish SBOMs as unrelated files or tags

Publishing a sidecar file or a tag-derived SBOM without a manifest subject loses the required artifact binding. OCI referrers, with the standard referrers-tag fallback, retain that binding on compatible and older registries.

## Infrastructure Needed

No new permanent infrastructure is required. OCI-referrer coverage needs test registries with and without the OCI Distribution Spec 1.1 Referrers API.
