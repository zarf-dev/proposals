## Summary

Software Bill of Materials (SBOM) should be an optional artifact for packaging alongside the container images they were built from. This enables users to control the fidelity of information they are packaging when they rely on the SBOM for downstream delivery or consumption.

## Motivation

The internals of the package today all dictate declarative packaging, except the outputs of package signing which require distinct and controlled inputs, and SBOMs which are generated by default or not included at all. This prevents optionality for allowing upstream systems of provenance - particularly the source of truth build or origination systems - to provide SBOMs which could have greater fidelity of information.

This also proposes tracking sboms, whether observed (generated by Syft by default) or declaratively defined, in the package build data such that we can accurately track and perform additional mapping required for future processes such as publishing to the registry during package deployment.

### Goals

- Allow each platform-specific image to declare one author-selected SBOM.
- Retain Syft image generation when a platform-specific image has no supplier SBOM, unless fallback generation is explicitly skipped.
- Bind each supplied SBOM to exactly one packaged image manifest and preserve that association through packaging and publication.
- Accept supplier SBOMs in explicitly supported formats, initially Syft JSON, SPDX JSON, and CycloneDX JSON, when they successfully decode according to their declared format.
- Preserve the accepted SBOM bytes in their declared format as the canonical package inventory.
- Retain one canonical SBOM for each packaged image manifest when a supplier document is provided or generation is enabled, and publish it when Zarf pushes that image to a registry.
- Record every image SBOM observed during package creation, whether generated by Zarf or supplied declaratively, in build data.
- Represent each packaged platform image with its resolved immutable digest.

### Non-Goals

- Select among multiple matching supplier SBOMs. An OCI-referrer source without a descriptor digest succeeds only when the selected leaf manifest has exactly one matching referrer.
- Treat an image-index SBOM as a per-platform SBOM. Index-level aggregate SBOMs are outside this proposal.
- Merge two independently produced SBOM inventories.
- Augment an SBOM with any additional information that requires SBOM-specific logic in Zarf.
- Add declarative SBOM ingestion or generation for files. Existing file packaging behavior is unchanged.

## Proposal

Zarf will associate an optional supplier SBOM with each platform-specific image manifest entry. Each entry identifies a platform and may pin an image manifest with a digest. It may also contain an SBOM format and source. When the digest is omitted, Zarf resolves the image reference for the declared platform during package creation and uses the resolved immutable digest for SBOM association and build metadata. Zarf preserves the supplied document and publishes it with the corresponding image. When an entry has no supplier SBOM, Zarf generates one with Syft unless the existing SBOM-skip option is enabled. The option suppresses only fallback generation. Explicitly declared supplier SBOMs remain required inputs and are retrieved, decoded, preserved, and recorded normally. Every accepted image SBOM, whether supplier-provided or generated, is recorded in `BuildData.SBOMs`. A declared source that cannot be retrieved, verified, or successfully decoded according to its declared format causes package creation to fail.

### Terminology

- **Image reference:** The name a package author writes, such as `registry.example/app:1.2.3`.
- **Platform-specific image:** One build of that image for an operating system and architecture, such as `linux/amd64`.
- **Image manifest:** The OCI object describing one platform-specific image. Its digest is the immutable identifier for that exact image.
- **Image index:** An OCI object that points to multiple platform-specific image manifests.

The proposal uses “leaf manifest” in the technical sections as shorthand for a platform-specific image manifest, to distinguish it from an image index.

```yaml
components:
  - name: application
    images:
      - name: registry.example/app:1.2.3
        manifests:
          - platform: linux/amd64
            digest: sha256:image-amd64
            sbom:
              format: cyclonedx-json
              source:
                ociReferrer: {}

          - platform: linux/arm64
            digest: sha256:image-arm64
            sbom:
              format: cyclonedx-json
              source:
                local:
                  path: ./sboms/app-arm64.json
```

Each `manifests[]` entry identifies one platform-specific image. `platform` is required; `digest` is optional. A supplied digest pins the image manifest and must identify the image for the declared platform. When the digest is omitted, Zarf resolves exactly one image manifest for the declared platform from the image reference during package creation. An image index or tag resolving to an index requires one entry per packaged platform when supplier SBOMs are declared. Zarf must not apply one platform's supplier SBOM to another platform. A manifest entry without an SBOM uses the Syft fallback unless the existing SBOM-skip option is enabled.

If `manifests[].digest` is supplied, Zarf verifies that it matches the declared platform. If it is omitted, Zarf records the resolved digest in `BuildData.SBOMs` and uses it for SBOM retrieval, association, and publication. Failure to resolve exactly one matching manifest stops package creation. Omitting the digest reduces maintenance overhead but allows a mutable tag or index to resolve to different image content across package creations; supplying a digest remains the reproducible-build option. A supplier document may be reused as stored content for multiple platforms only when each association is declared explicitly.

### User Stories

#### Story 1: Consume a supplier SBOM

As a package author, I want to include the SBOM produced by an upstream image builder to the image I package, so the package retains the inventory generated by that release process.

#### Story 2: Prepare and enrich an SBOM

As a package author consuming an image produced by another team or vendor, I want to obtain or generate an SBOM for the exact platform-specific image, enrich it with additional product or package metadata, and provide the resulting SBOM to Zarf, so I can preserve the inventory I need without requiring Zarf to perform the enrichment.

#### Story 3: Consume the published SBOM

As a downstream scanner or operator, I want the preserved SBOM to remain attached to the exact image manifest it describes, so I can retrieve the intended inventory from the target registry.

### Risks and Mitigations

#### Wrong image or platform association

**Risk:** A supplied SBOM may describe a different image or platform.

**Mitigation:** Bind every supplier SBOM to one platform-specific image manifest digest. OCI referrers must have a matching `subject`. Later validation will require direct SBOM subject evidence or verified external binding before treating the payload association as proven.

#### Mutable image references

**Risk:** When `manifests[].digest` is omitted, the same tag or image index may resolve to different platform-specific image content across package creations.

**Mitigation:** Resolve exactly one image manifest for the declared platform during package creation and record the resolved immutable digest in `BuildData.SBOMs`. Authors that require reproducible image selection can provide the digest explicitly.

#### SBOM correctness and completeness

**Risk:** A supplier SBOM may be validly encoded and correctly associated with an image while still being incomplete, inaccurate, or intentionally misleading. A valid signature proves that a trusted signer made or approved the claim; it does not prove that the claim is semantically correct.

**Mitigation:** Zarf validates source integrity, format validity, and image association to a defined extent, but cannot generally prove that an SBOM truthfully or completely describes an image. Preserve supplier bytes and source evidence, distinguish a declared association from an independently validated association, and do not present association validation as content-correctness validation. Downstream consumers remain responsible for trust and completeness policy.

#### Input and output fidelity

**Risk:** Converting a supplier SBOM can discard producer-specific information.

**Mitigation:** Preserve the accepted document bytes and declared format as the canonical package inventory. Conversion is an explicit export operation and does not replace the preserved document.

#### Registry publication failure

**Risk:** A target registry may not support the OCI Referrers API, or concurrent publishers may update its fallback index.

**Mitigation:** Publish a subject-bound artifact using the Referrers API when available and the standard referrers-tag fallback otherwise. Preserve existing associations and fail if Zarf cannot confirm that the SBOM remains attached to the target image.

## Design Details

### Delivery Phases

#### Phase 1: Accept local SBOM sources

Allow each platform-specific image manifest entry to provide an SBOM through `sbom.source.local.path`. Package creation retrieves the document, decodes the declared format, preserves the exact bytes in the package's existing `sboms/` representation, and records the resolved association in `BuildData.SBOMs`. Images without a supplier SBOM retain the Syft fallback unless the existing SBOM-skip option is enabled. The option does not suppress explicitly declared supplier SBOMs.

#### Phase 2: Retrieve SBOMs from OCI sources

Support OCI-native SBOM retrieval from registry referrers. `ociReferrer` is one logical SBOM source: Zarf uses the OCI Referrers API when available and the standard referrers-tag mechanism as the discovery fallback. Retrieved documents continue to be preserved in the package's existing `sboms/` representation; this phase does not require changing package storage. Pinned referrers must identify the selected image manifest. Unpinned discovery must find exactly one matching referrer for that manifest.

#### Phase 3: Publish SBOMs with images

When Zarf pushes a packaged image manifest to a registry, it creates or publishes the preserved SBOM as a subject-bound artifact. Publication uses the OCI Referrers API when available and the standard referrers-tag fallback otherwise. Deployment must not generate a different SBOM or silently publish an SBOM for another platform.

Each source must be retrievable, preserve its exact bytes, successfully decode according to its declared format, and satisfy the association evidence available for that source. OCI sources require a matching subject. Build data records whether the image association is declared or validated. Zarf can validate source integrity, format, and association to a defined extent. It cannot generally prove that an SBOM is complete or correct.

Format-specific decoding is required before a supplier document is accepted. Decoding may extract format and version metadata and reject malformed or structurally invalid documents. Zarf preserves the original payload and does not convert it during package creation. This validation must not be presented as proof that the document accurately describes the image.

### SBOM selection

#### Image SBOM sources

Each `images[].manifests[]` entry contains a required `platform`, an optional image manifest `digest`, and an optional `sbom`. When present, `digest` pins the platform-specific image manifest. When omitted, Zarf resolves it during package creation. The `sbom` contains a supported `format` and exactly one source:

- `local.path` for a local SBOM document.
- `ociReferrer.digest` for an optionally pinned SBOM referrer in the image repository. The referrer source uses the OCI Referrers API when available and the standard referrers-tag mechanism as a fallback; these are discovery mechanisms for one source, not separate source types.

For an OCI referrer, Zarf requires the artifact's `subject` to match the resolved image manifest digest. Without a pinned referrer digest, Zarf accepts exactly one matching referrer and fails on zero or multiple matches, regardless of whether it was discovered through the Referrers API or the referrers-tag fallback. A manifest entry without `sbom` uses Syft unless the existing SBOM-skip option is enabled. One entry's SBOM must not implicitly apply to another platform.

During component import, manifest entries are merged by platform using the existing image merge behavior. Conflicting entries for the same platform fail rather than being selected by component order.

### Publication and provenance

Zarf's package SBOM is the accepted supplier document in its declared format, or the Syft-generated document when no supplier document is declared. The package preserves the document bytes, format, source evidence, platform, and image manifest digest as one association. During package creation, Zarf records every accepted image SBOM in `BuildData.SBOMs`, including the image manifest identity, platform, SBOM payload identity, format, and whether the document was provided or generated.

#### build-data records

`BuildData.SBOMs` is an collection of observations. Each record contains:

- `subject.kind`, identifying what the SBOM describes, currently `image`.
- `subject.component`, identifying the package component that owns the subject.
- `subject.identity`, containing kind-specific identity such as an image reference, platform, and manifest digest.
- `format`, identifying the preserved document format.
- `payloadDigest`, identifying the preserved SBOM bytes.
- `origin`, identifying whether the document was `generated` by Zarf or `supplier`-provided.
- `source`, containing retrieval or generation evidence.
- `association`, recording whether the subject relationship is declared or validated.

Future component-level SBOM observations can use the same record envelope with `subject.kind: component` and a component-specific identity. The build data records the observation and its provenance; it does not replace the preserved SBOM document.


### Registry publication

For every packaged image manifest, deployment reads the matching `subject.kind: image` record from `BuildData.SBOMs` and publishes the associated preserved SBOM to the target image repository. The published artifact is subject-bound to that image manifest, uses the recorded SBOM format, and is idempotent. Existing unrelated referrers must remain intact. Publication failure must fail deployment rather than silently omitting the SBOM.

### Test Plan

- Phase 1 tests cover manifest-level platform and digest mappings, including pinned and omitted digests; local SBOM retrieval; format decoding; exact-byte preservation in the package's `sboms/` representation; recording `BuildData.SBOMs` entries for supplier-provided and fallback-generated SBOMs; skip behavior for fallback generation; explicit supplier SBOMs remaining effective when generation is skipped; aliases; final packaged manifests; source and origin metadata; conflicting mappings; and rejection of cross-platform reuse.
- Phase 2 tests cover OCI-layout retrieval, pinned and unpinned registry referrer retrieval, Referrers API and referrers-tag fallback behavior, subject mismatches, zero or multiple matches, malformed responses, and invalid digests.
- Phase 3 tests cover subject-bound publication, idempotent repeated publication, preservation of unrelated referrers, and deployment failure when publication cannot be confirmed.
- Cross-cutting validation tests cover declared versus validated associations, format/media-type handling, and the boundary between association validation and SBOM semantic correctness.
- Compatibility tests cover creation of `BuildData.VersionRequirements`, deployment rejection by an older CLI, and preservation of SBOM observations during schema conversion.

### Upgrade / Downgrade Strategy

Image manifest entries without supplier `sbom` retain current Syft generation behavior unless the existing SBOM-skip option is enabled, and generated documents are recorded in `BuildData.SBOMs`. With the option enabled, explicit supplier SBOMs continue to be packaged while fallback generation is omitted and reported. File SBOM ingestion and generation remain unchanged and outside this ZEP. Package creation must add a `BuildData.VersionRequirements` entry for the minimum Zarf version that understands and preserves SBOM records.

Removing an entry's supplier `sbom` restores generated inventory for that image platform when fallback generation is enabled. Removing a supplier SBOM from a package definition does not alter preserved bytes in packages that were already built.

### Version Skew Strategy

This feature changes the v1beta1 package schema and depends on the platform-aware image resolution contract. Schema migration must preserve `BuildData.SBOMs` records, their subject identity and provenance, and the related `BuildData.VersionRequirements` entry. It must reject conversions that cannot represent those observations without loss.

## Drawbacks

This adds schema, source-validation, format-aware package inspection, and provenance complexity to package creation.

## Alternatives

### Continue generating SBOMs exclusively with Syft

Syft remains the fallback, but exclusive generation discards an application producer's authoritative inventory and cannot reliably infer every primary application identity.

### Augment SBOMs to discovered packages

Appending a declared identity to a dependency or Go-module component conflates product identity with dependency identity and is not a reliable scanner interoperability model.

### Merge multiple SBOMs

Zarf accepts only one supplier SBOM for a manifest. No general component identity or relationship merge is safe across independent SBOM producers.

### Publish SBOMs as unrelated files or tags

Publishing a sidecar file or a tag-derived SBOM without a manifest subject loses the required artifact binding. OCI referrers, with the standard referrers-tag fallback, retain that binding on compatible and older registries.

### Store image SBOMs in the package OCI layout

An alternative is to store every accepted image SBOM as an OCI artifact in the package's OCI layout instead of preserving the payload in the `sboms/` directory. Each SBOM artifact would be subject-bound to the final platform-specific image manifest, with its payload media type and format represented by the artifact metadata. `BuildData.SBOMs` could remain as an index of the stored artifacts and their provenance, while the OCI layout would become the canonical payload and association store.

This would provide a native OCI relationship inside the package, allow OCI-aware tooling to traverse image-to-SBOM associations, and reduce the need to construct the artifact wrapper during registry publication. It would also require changes to package image retrieval and inspection so they distinguish image manifests from SBOM artifacts, preserve referrer relationships when copying or extracting layouts, and remain compatible with older packages and clients that expect the layout to contain only image content. Package assembly, archive accounting, garbage collection, and migration would also need to account for the additional OCI artifacts.

The current proposal does not select this alternative. It retains SBOM payloads in the existing `sboms/` representation and materializes a subject-bound OCI referrer during publication, avoiding changes to current OCI image storage and retrieval behavior. OCI-layout storage remains a possible future direction if Zarf adopts an OCI artifact graph as the canonical package representation.

## Infrastructure Needed

No new permanent infrastructure is required. OCI-referrer coverage needs test registries with and without the OCI Distribution Spec 1.1 Referrers API.
